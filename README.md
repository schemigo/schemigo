# schemigo

Декларативное управление схемами PostgreSQL, MySQL и ClickHouse.

Реализованы общая модель схемы, `Normalize`, SQL-план с SHA-256, контракт драйвера и `postgres.Open(dsn)` для создания пула pgx из URL или keyword DSN. `Open` проверяет формат DSN без подключения; доступность сервера проверяется через `PingContext`, пул закрывается вызывающим кодом. Чтение каталогов PostgreSQL 15+ через `postgres.New().Inspect(ctx, conn, schemaName)` поддерживает таблицы, enum, extensions, функции, триггеры и views. Diff PostgreSQL поддерживает extensions, enum, таблицы, колонки и PK; изменения других сущностей пока возвращают `errors.ErrUnsupported`. Unit- и интеграционные тесты прошли на PostgreSQL 18; другие версии пока не проверены. Экспорт и применение миграций ещё не реализованы. CLI выводит сообщение об отсутствии реализации и завершается с кодом 1.

`Driver.Diff` только строит план. Extensions создаются и обновляются до заданной версии, лишние не удаляются. Enum поддерживают создание, добавление значений с сохранением порядка, удаление и перестановку значений через пересоздание типа. Пересоздание требует подключения для проверки зависимостей и выполняется одним атомарным DO-блоком: ошибка откатывает временный тип и изменения колонок/defaults. Неизвестные зависимости и существующий временный тип не удаляются; изменение owner/ACL при пересоздании вызывает отказ, комментарий типа сохраняется.

Для таблиц и колонок поддерживаются создание, удаление, изменение типа с `Using`, default, NOT NULL и состава PK. Переименование определяется только по единственному совпадению определения без имени; неоднозначность возвращает ошибку. SQL проверяет определения при переименовании и повторном выполнении, а преобразование типа и замена default выполняются атомарно. Удаления и преобразования типов отмечены `Destructive`; `CASCADE` не используется, удаление колонки с зависимыми объектами отклоняется.

Новые колонки добавляются в конец; перестановка колонок не поддерживается. Добавление/изменение индексов, FK и CHECK относится к задаче 6; изменения функций, триггеров и views — к задаче 7. Переименование с зависимыми views или колонок с CHECK/выражениями индексов/условиями триггеров пока отклоняется. Для сложных типов и выражений default сравнение текстовое: используйте каноническую запись из `Inspect`. SQL таблиц временно устанавливает `search_path` в `pg_catalog` и управляемую схему и восстанавливает исходное значение.

Для исполнения плана используют `Statements`, учитывая `OutsideTransaction`: добавление enum-значения должно завершиться autocommit до следующего statement, который его использует. `Plan.SQL()` предназначен для просмотра и хеша и не кодирует границы транзакций. Общий Apply пока не реализован.

## Структура

| Каталог или файл | Назначение |
| --- | --- |
| `schema.go`, `validate.go` | Общая модель схемы и валидация |
| `plan.go`, `driver.go` | План SQL и контракт диалектов |
| `migrate.go` | Планирование, применение, история и снимки схемы |
| `export.go`, `load.go` | Экспорт и загрузка Go-схемы |
| `cmd/schemigo/` | CLI и генерация шаблонов |
| `postgres/` | Диалект PostgreSQL |
| `mysql/` | Диалект MySQL |
| `clickhouse/` | Диалект ClickHouse и координация блокировок |
| `internal/testdb/` | Запуск одноразового PostgreSQL для интеграционных тестов |
| `docs/superpowers/plans/` | План реализации |

Файлы `*_test.go` добавляются рядом с реализацией по мере разработки. Интеграционные тесты отделены тегом `integration`. Каталог `schema/` — будущий результат экспорта пользовательской схемы, а не внутренний пакет инструмента.

## Разработка

Версия Go в существующем `go.mod`: **1.27**. Команды ниже требуют соответствующего toolchain:

```sh
go vet -mod=readonly ./...
go test -mod=readonly ./...
go build -mod=readonly ./...
```

Unit-тесты модели, валидации, SQL-плана и PostgreSQL inspector работают без БД. Модули pgx и testcontainers подключены для интеграционных проверок; версия Go остаётся 1.27. Разрешены fixtures в одноразовых контейнерах PostgreSQL; ограничения на применение к существующим БД сохраняются в [плане](docs/superpowers/plans/2026-11-09-schemigo.md).

Интеграционные тесты используют pgx и testcontainers из `go.mod`. Для запуска нужны Docker и команда `SCHEMIGO_TESTCONTAINERS=1 go test -mod=readonly -tags=integration ./...`. Helper лениво запускает один контейнер PostgreSQL 18 на тестовый пакет; каждый вызов `testdb.Postgres(t)` создаёт отдельную БД из `template0` и удаляет её через `t.Cleanup`. `TestMain` вызывает `os.Exit(testdb.Run(m))`, чтобы удалить контейнер после завершения всех тестов. Параллельные тесты используют независимые БД; роли и другие объекты уровня кластера нужно явно очищать. Без переменной включения тесты с тегом `integration` собираются и пропускают запуск контейнера.

GitHub Actions запускает все unit- и интеграционные тесты при открытии/повторном открытии PR и каждом пуше в его ветку (`pull_request: synchronize`). Workflow [Tests](.github/workflows/tests.yml) использует Go из `go.mod`, PostgreSQL 18 и `-race`, без кеширования результатов тестов. В логе старт пакета выделен голубым, успешные тесты — зелёным, упавшие — красным, пропущенные — жёлтым. Шаг `Report test failures` выводит обычные строки: пакет, статус, длительность и счётчики passed/failed/skipped. Summary показывает те же данные в таблице со статусами ✅/❌/⏭️ и общим итогом; счётчики включают subtests. Ниже в обоих представлениях выводятся имя упавшего теста и диагностический контекст, включая ошибки сборки. Длительность пакета берётся из `go test -json`; значение меньше миллисекунды обозначается `<0.001s`, отсутствие времени при ошибке сборки — `n/a`. Показатель `0s` рядом с шагом отчёта означает округлённое время его генерации, а не длительность тестов. Ссылка на Summary выводится в конце отчёта. Полные JSON-логи, stderr и покрытие сохраняются в артефакте `test-results` на 14 дней.

Слияние PR в основную ветку разрешается только после успешного `All tests (PostgreSQL 18)` на актуальной версии ветки. Для этого подготовлен [ruleset](.github/rulesets/required-tests.json): обязательный PR и status check, без bypass-исключений. **Файл в репозитории не включает защиту автоматически.** Администратор должен [импортировать ruleset](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository#importing-a-ruleset) через [Settings → Rules → Rulesets](https://github.com/alaleks/schemigo/settings/rules) → New ruleset → Import a ruleset, проверить `Active`, основную ветку и обязательный check, затем нажать Create. Проверка включения: PR с упавшим или ещё не завершившимся check должен блокировать Merge, в том числе для администратора без bypass. Применение правила на GitHub из текущего окружения не выполнялось: авторизация API отсутствует.

Inspector исключает `schema_migrations`, объекты расширений и constraint triggers. Поддерживаются триггеры на таблицах и обычных views, включая `INSTEAD OF`; materialized views не могут быть целью триггера. Для свойств вне текущей модели, например identity/generated columns, partitioning, UNIQUE constraints, INCLUDE indexes, cross-schema FK и расширенных опций функций, возвращается ошибка. PostgreSQL Validate, Lock и методы истории пока возвращают `errors.ErrUnsupported`.
