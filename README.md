# schemigo

Декларативное управление схемами PostgreSQL, MySQL и ClickHouse.

Реализованы общая модель схемы, `Normalize`, SQL-план с SHA-256, контракт драйвера и `postgres.Open(dsn)` для создания пула pgx из URL или keyword DSN. `Open` проверяет формат DSN без подключения; доступность сервера проверяется через `PingContext`, пул закрывается вызывающим кодом. Чтение каталогов PostgreSQL 15+ через `postgres.New().Inspect(ctx, conn, schemaName)` поддерживает таблицы, enum, extensions, функции, триггеры и views. Diff PostgreSQL поддерживает extensions, enum, таблицы, колонки, PK, индексы, FK, CHECK, функции, триггеры и views. Этапы 1–7 проверены на PostgreSQL 18; полный локальный прогон unit- и интеграционных тестов с `-race` и `-shuffle=on` прошёл. Экспорт и загрузка Go-схемы, применение миграций и история PostgreSQL реализованы. CLI поддерживает экспорт, просмотр SQL, применение и историю миграций PostgreSQL.

`Driver.Diff` только строит план. Extensions создаются и обновляются до заданной версии, лишние не удаляются. Enum поддерживают создание, добавление значений с сохранением порядка, удаление и перестановку значений через пересоздание типа. Пересоздание требует подключения для проверки зависимостей и выполняется одним атомарным DO-блоком: ошибка откатывает временный тип и изменения колонок/defaults. Неизвестные зависимости и существующий временный тип не удаляются; изменение owner/ACL при пересоздании вызывает отказ, комментарий типа сохраняется.

Для таблиц и колонок поддерживаются создание, удаление, изменение типа с `Using`, default, NOT NULL и состава PK. Переименование определяется только по единственному совпадению определения без имени; неоднозначность возвращает ошибку. SQL проверяет определения при переименовании и повторном выполнении, а преобразование типа и замена default выполняются атомарно. Удаления и преобразования типов отмечены `Destructive`; DROP не использует `CASCADE`. Управляемые зависимости колонки снимаются заранее, неизвестные зависимости приводят к отказу.

Индексы поддерживают Columns, Unique, Expression, Where и Method, включая GIN. Expression содержит SQL списка ключей индекса; арифметические выражения требуют скобок по синтаксису PostgreSQL, например `(id + 1)`. Изменение определения выполняется через DROP и CREATE. Имена индексов проверяются на уникальность во всей схеме. FK удаляются до индексов/колонок/PK/таблиц и добавляются после создания всех таблиц и уникальных ключей; поддерживаются составные и циклические FK, OnDelete и OnUpdate. При замене опорного PK/индекса или типов колонок зависимые FK временно снимаются даже без изменения их определения. CHECK и FK добавляются как NOT VALID и валидируются в одном DO-блоке; ошибка не оставляет невалидированное ограничение. При конфликте имени или изменении удаляемого объекта SQL отказывает с предложением построить план заново.

Новые колонки добавляются в конец; перестановка колонок не поддерживается. Изменение типов/удаление колонок и переименование таблиц требуют снятия и восстановления зависимых управляемых views. Переименование колонок с CHECK/выражениями индексов/условиями триггеров пока отклоняется. Сравнение выражений индексов/CHECK учитывает пробелы, комментарии и внешние скобки, сохраняя литералы и quoted identifiers; неявные casts и другие преобразования SQL не нормализуются — для таких выражений используйте каноническую запись из `Inspect`. Для сложных типов/defaults сравнение остаётся текстовым. SQL таблиц временно устанавливает `search_path` в `pg_catalog` и управляемую схему и восстанавливает исходное значение.

`PlanMigration` строит SQL без применения. `Apply` повторно строит план под advisory lock, сохраняет Go-снимок текущей схемы в `schemigo_backup/`, исполняет обычные statements транзакциями и `OutsideTransaction` в autocommit, затем записывает SHA-256 плана, время и пользователя БД в `schema_migrations`. При ошибке снимок остаётся на диске и его путь доступен через `ApplyError.BackupPath`; это снимок объектов, а не резервная копия данных. При пустом diff история не пополняется; повторный хеш не блокирует устранение drift. Обычный SQL и запись истории фиксируются одной транзакцией; операторы OutsideTransaction остаются зафиксированными при последующей ошибке. `History` читает журнал без создания таблицы. Индексы строятся обычным CREATE INDEX, который может блокировать запись; CONCURRENTLY пока не поддерживается. `Plan.SQL()` предназначен для просмотра и хеша и не кодирует границы транзакций.

Функции сравниваются по имени и типам входных аргументов; имена параметров, defaults и OUT-параметры не входят в идентификатор перегрузки. Модификаторы встроенных типов аргументов/результата не учитываются, как и в PostgreSQL. Изменение тела выполняется через CREATE OR REPLACE; изменение результата, имён параметров или удаление defaults требует пересоздания и проверки зависимостей. Тела функций сохраняются и сравниваются побайтно. Поддерживаются языки sql и plpgsql и свойства из модели; произвольный SQL остаётся доверенным кодом пользователя.

Обычные views заменяются через CREATE OR REPLACE, если PostgreSQL подтвердил совместимость имён, порядка, типов и модификаторов существующих колонок. Для этого pgx описывает запрос в read-only транзакции без выполнения SELECT; локальный search_path восстанавливается при выходе. Несовместимые изменения и materialized views требуют пересоздания. Зависимые управляемые views снимаются в обратном порядке и восстанавливаются; триггеры на них создаются повторно. Неизвестные зависимости, отличающийся владелец, grants (включая права колонок), комментарии и неподдерживаемые параметры пересоздаваемого объекта вызывают отказ. DROP использует RESTRICT, без CASCADE. Удаление materialized view отмечено Destructive.

Для изменений существующих views и пересоздания функций нужен conn, полученный из postgres.Open. Новые объекты и обычную замену функций/триггеров можно планировать без соединения. Порядок новых views и вызовов функций выводится консервативно из SQL-токенов: неоднозначные/циклические ссылки отклоняются, динамический SQL не анализируется. Для views совпадение имени колонки или CTE с именем управляемого view может дать ложную зависимость. Сложные типы, casts и семантически эквивалентные выражения не канонизируются полностью; используйте запись из Inspect. Например, `FROM public.users` и `FROM users` в определении view считаются разными и могут оставлять повторный diff непустым. Изменение функции, от которой зависит default/CHECK/индекс таблицы, может потребовать отдельного этапа: такие зависимости не пересоздаются автоматически. Вспомогательные запросы ничего не применяют; схема и SQL должны происходить из доверенного источника.

## Экспорт и загрузка Go-схемы

`schemigo.Export(ctx, db, driver, schemaName, dir)` читает схему через `Driver.Inspect` и создаёт её редактируемое Go-описание. `schemigo.Load(ctx, dir)` компилирует это описание, запускает его и возвращает нормализованную `Schema`.

```go
err := schemigo.Export(ctx, db, postgres.New(), "public", "./schema")
if err != nil {
    return err
}
desired, err := schemigo.Load(ctx, "./schema")
```

В `schema/` создаются `main.go` и пакеты `extensions`, `enums`, `tables`, `functions`, `triggers`, `views`. Каждый пакет содержит `types.go` с aliases, `all.go` со списком `All` и отдельный файл для каждой сущности, например `tables/users_schema.go`. При коллизиях имён добавляется стабильный суффикс; перегрузки функций и одинаковые имена триггеров разных таблиц сохраняются. При ручном добавлении сущности её нужно включить в `All`. Экспорт сохраняет порядок объектов и `Schema.Order`, но не закрепляет `Extension.Version`.

Каталог должен находиться внутри текущего Go-модуля, иметь допустимый переносимый ASCII import path и не пересекать вложенный модуль или символическую ссылку. `go.work` с несколькими модулями поддерживается. Для экспорта каталог должен отсутствовать или быть пустым: существующие файлы не перезаписываются. Сначала генерируется полное содержимое во временной соседней директории, затем оно публикуется переименованием.

`Load` выполняет **доверенный Go-код** со всеми правами процесса. В `PATH` должен быть подходящий Go toolchain. Компиляция использует `go build -mod=readonly`; зависимостями управляет вызывающий проект. Затем запускается временный бинарник, чтобы отмена context завершала сам процесс схемы. Если схема запускает дочерние процессы, она отвечает за их жизненный цикл. Stdout должен содержать ровно один JSON-объект схемы; stderr используется для диагностики. Ошибки компиляции и выполнения возвращаются с диагностикой, лишний stdout и невалидная схема отклоняются.

## CLI PostgreSQL

```sh
schemigo -d 'postgres://user:password@localhost/db?sslmode=disable' -export
schemigo -d 'postgres://user:password@localhost/db?sslmode=disable' -dry-run
schemigo -d 'postgres://user:password@localhost/db?sslmode=disable' -yes
schemigo -d 'postgres://user:password@localhost/db?sslmode=disable' -history
```

По умолчанию Go-схема читается из `./schema`, управляемая схема БД — `public`. Их можно изменить через `-dir` и `-schema`. Без `-yes` CLI показывает SQL и запрашивает `Y/n`; пустой ответ и `n` отменяют применение. Перед применением показанный план сверяется с новым планом под блокировкой; при изменении БД CLI попросит просмотреть SQL заново. `-dry-run` только показывает план и не создаёт журнал или снимок. `-no-backup` отключает снимок перед применением. При ошибке применения выводится точный путь сохранённого снимка. Для терминала выделяются основные SQL-команды ANSI-цветом, а в pipe или файл выводится обычный SQL. Для этой подсветки новая зависимость не добавлялась.

## ClickHouse

Реализованы `clickhouse.Open`, `clickhouse.New`, Inspect/Diff, Export/Load, Apply и история на MergeTree. CLI принимает `clickhouse://`; база по умолчанию берётся из URL (или `default`), `-schema` переопределяет её.

```sh
schemigo -d 'clickhouse://localhost:9000/analytics' -export
schemigo -d 'clickhouse://localhost:9000/analytics' -dry-run
schemigo -d 'clickhouse://localhost:9000/analytics' -keeper 'localhost:2181' -yes
schemigo -d 'clickhouse://localhost:9000/analytics' -history
```

Для Go API создайте `locker, err := clickhouse.NewKeeperLocker(ctx, endpoints, "/schemigo")`, проверьте ошибку и закройте locker через `defer locker.Close()`. Передайте `clickhouse.New(locker)` в `schemigo.Apply`. `clickhouse.New(nil)` поддерживает чтение, экспорт и diff; Apply отказывает до DDL. Dry-run/export/history не подключаются к Keeper, даже если передан `-keeper`.

Поддерживаются таблицы с обязательным `Engine` и SQL clauses `OrderBy`/`PartitionBy`, колонки с native Type и DEFAULT, skipping indexes с `Type` и положительной `Granularity`, CHECK, SQL lambda functions, обычные и materialized views. Nullable задаётся в Type, например `Nullable(String)`; `Table.PrimaryKey` содержит имена колонок отдельного первичного ключа. Engine содержит имя и аргументы движка, например `ReplacingMergeTree(version)`, и при необходимости `SETTINGS ...`; настройки сохраняются при экспорте. Изменение engine, partition или primary key требует ручной миграции данных. Extensions, отдельные enum, FK, triggers, unique/partial indexes, MATERIALIZED/ALIAS columns и непредставимые table clauses (`TTL`, `SAMPLE BY`) возвращают ошибку.

`Function.Parameters` — список аргументов lambda, `Body` — её выражение; Returns и перегрузки не поддерживаются. **SQL-функции глобальны для сервера:** Inspect включает все SQL UDF, и отсутствие функции в desired означает её удаление независимо от базы. Поэтому все миграции используют общую очередь блокировки, включая разные базы. Все клиенты одного сервера должны использовать одинаковые Keeper endpoints и path; CLI использует `/schemigo`. Координатор должен находиться в доверенной сети: создаваемые znodes используют world ACL. Клиентские изменения в обход этой блокировки не координируются.

`View.Definition` содержит SELECT обычного view; для materialized view — `TO db.target AS SELECT ...` либо `ENGINE = MergeTree ORDER BY ... AS SELECT ...`. Inspect сохраняет также явные колонки и security clauses. При пересоздании существующие DEFINER/SQL SECURITY сохраняются, если desired не задаёт их явно. Пересоздание materialized view с собственным storage удаляет накопленные данные и отмечается Destructive. Views создаются после таблиц и функций; зависимости между views/functions определяются консервативно по SQL-токенам. Совпадение имени объекта с именем колонки может дать ложную зависимость. Сравнение выражений не является полной SQL-канонизацией; при повторном diff используйте запись из Inspect.

DDL выполняется без общей транзакции. История записывается только после полного успеха; пустой diff не добавляет событие, ранее встречавшийся хеш не мешает устранению drift. После ошибки повторный Apply заново читает схему и строит оставшийся diff. Снимок содержит только схему и не восстанавливает удалённые данные.

Keeper использует ephemeral sequential znode и watch без polling. Закрытие сессии освобождает lock. При любом disconnect locker становится непригоден для повторного использования, отменяет контекст Apply и останавливает дальнейшие statements. **Уже принятый ClickHouse запрос может завершиться после потери сессии: строгая защита от split-brain не гарантируется.** Пользовательский Locker должен предоставлять `MigrationContext(context.Context) (context.Context, context.CancelFunc)` для уведомления о потере владения; без него Apply видит только отмену контекста вызывающего кода.

Unit/race/vet проверки и интеграционные сценарии на реальных ClickHouse 25.8 и ZooKeeper 3.9.3 проходят. GitHub Actions запускает отдельные jobs PostgreSQL 18 и ClickHouse 25.8, с `-race`, `-shuffle=on`, `-count=1`, отчётами и покрытием. ClickHouse fixtures создают одноразовые контейнеры через testcontainers; PostgreSQL job исключает `TestClickHouse*`, а ClickHouse job запускает их, включая CLI. Оба check указаны в `.github/rulesets/required-tests.json`. Локальный запуск:

```sh
SCHEMIGO_TESTCONTAINERS=1 GOTOOLCHAIN=local go test -mod=readonly -tags=integration ./clickhouse ./cmd/schemigo -run ClickHouse -v
```

## Генерация Go-схемы

Команды ниже создают `./schema`, если каталог ещё не существует, или добавляют сущность в экспортированную схему. Подключение к БД не требуется. Флаги команды ставятся перед именем сущности; `-dir` задаёт другой каталог, а `-schema` — имя схемы при создании нового каталога (по умолчанию `public`).

```sh
schemigo table users 'id:int8,email:varchar(255),total:numeric(10,2)'
schemigo enum order_status 'pending,processing,shipped,delivered,cancelled'
schemigo view active_users ./active_users.sql
schemigo view -materialized user_totals ./user_totals.sql
```

Новая сущность включается в соответствующий `all.go` и сразу видна через `Load`. View получает отдельный SQL-файл в `schema/views/`: редактируйте его без экранирования текста в Go. Существующие файлы сущностей не перезаписываются; повторное имя или некорректный список колонок/значений возвращают ошибку.

## Структура

| Каталог или файл | Назначение |
| --- | --- |
| `schema.go`, `validate.go` | Общая модель схемы и валидация |
| `plan.go`, `driver.go` | План SQL и контракт диалектов |
| `migrate.go` | Планирование, применение, история и снимки схемы |
| `export.go`, `load.go`, `scaffold.go` | Экспорт, загрузка и добавление сущностей Go-схемы |
| `cmd/schemigo/` | CLI миграций и генерация схемы |
| `postgres/` | Диалект PostgreSQL |
| `mysql/` | Диалект MySQL |
| `clickhouse/` | Диалект ClickHouse и координация блокировок |
| `internal/testdb/` | Запуск одноразового PostgreSQL для интеграционных тестов |
| `docs/superpowers/plans/` | План реализации |

Файлы `*_test.go` добавляются рядом с реализацией по мере разработки. Интеграционные тесты отделены тегом `integration`. Каталог `schema/` — будущий результат экспорта пользовательской схемы, а не внутренний пакет инструмента.

## Разработка

Версия Go в существующем `go.mod`: **1.27**. Команды ниже требуют соответствующего toolchain:

```sh
go vet -mod=readonly ./...
go test -mod=readonly ./...
go build -mod=readonly ./...
```

Unit-тесты модели, валидации, SQL-плана и PostgreSQL inspector работают без БД. Модули pgx и testcontainers подключены для интеграционных проверок; версия Go остаётся 1.27. Разрешены fixtures в одноразовых контейнерах PostgreSQL; ограничения на применение к существующим БД сохраняются в [плане](docs/superpowers/plans/2026-11-09-schemigo.md).

Интеграционные тесты используют pgx и testcontainers из `go.mod`. Для запуска нужны Docker и команда `SCHEMIGO_TESTCONTAINERS=1 go test -mod=readonly -tags=integration ./...`. Helper лениво запускает один контейнер PostgreSQL 18 на тестовый пакет; каждый вызов `testdb.Postgres(t)` создаёт отдельную БД из `template0` и удаляет её через `t.Cleanup`. `TestMain` вызывает `os.Exit(testdb.Run(m))`, чтобы удалить контейнер после завершения всех тестов. Параллельные тесты используют независимые БД; роли и другие объекты уровня кластера нужно явно очищать. Без переменной включения тесты с тегом `integration` собираются и пропускают запуск контейнера.

GitHub Actions запускает все unit- и интеграционные тесты при открытии/повторном открытии PR и каждом пуше в его ветку (`pull_request: synchronize`). Workflow [Tests](.github/workflows/tests.yml) использует Go из `go.mod`, PostgreSQL 18 и `-race`, без кеширования результатов тестов. В логе старт пакета выделен голубым, успешные тесты — зелёным, упавшие — красным, пропущенные — жёлтым. Шаг `Report test failures` выводит обычные строки: пакет, статус, длительность и счётчики passed/failed/skipped. Summary показывает те же данные в таблице со статусами ✅/❌/⏭️ и общим итогом; счётчики включают subtests. Ниже в обоих представлениях выводятся имя упавшего теста и диагностический контекст, включая ошибки сборки. Длительность пакета берётся из `go test -json`; значение меньше миллисекунды обозначается `<0.001s`, отсутствие времени при ошибке сборки — `n/a`. Показатель `0s` рядом с шагом отчёта означает округлённое время его генерации, а не длительность тестов. Ссылка на Summary выводится в конце отчёта. Полные JSON-логи, stderr и покрытие сохраняются в артефакте `test-results` на 14 дней.

Параллельно с тестами CI проверяет сборку Linux/amd64, Windows/amd64 и macOS (darwin/amd64, darwin/arm64). Все цели компилируются на Linux с `CGO_ENABLED=0`; `go build -mod=readonly -o "$RUNNER_TEMP/build/" ./...` проверяет все обычные пакеты и линкует CLI. Зависимости и результаты компиляции кешируются отдельно для каждой цели и версии Go. Контейнеры и тесты повторно в build-job не запускаются, бинарники не публикуются. Это проверка кросс-компиляции; запуск программ на Windows/macOS не проверяется.

Слияние PR в основную ветку разрешается только после успешного `All tests (PostgreSQL 18)` и всех четырёх `Build (...)` на актуальной версии ветки. Для этого подготовлен [ruleset](.github/rulesets/required-tests.json): обязательный PR и status checks, без bypass-исключений. **Файл в репозитории не включает защиту автоматически.** Администратор должен [импортировать ruleset](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository#importing-a-ruleset) через [Settings → Rules → Rulesets](https://github.com/alaleks/schemigo/settings/rules) → New ruleset → Import a ruleset, проверить `Active`, основную ветку и обязательные checks, затем нажать Create. Если правило уже создано, нужно добавить в него четыре build-check’а. Проверка включения: PR с упавшим или ещё не завершившимся check должен блокировать Merge, в том числе для администратора без bypass. Применение правила на GitHub из текущего окружения не выполнялось: авторизация API отсутствует.

Inspector исключает `schema_migrations`, объекты расширений и constraint triggers. Поддерживаются триггеры на таблицах и обычных views, включая `INSTEAD OF`; materialized views не могут быть целью триггера. Для свойств вне текущей модели, например identity/generated columns, partitioning, UNIQUE constraints, INCLUDE indexes, cross-schema FK и расширенных опций функций, возвращается ошибка. PostgreSQL поддерживает Validate, Lock и методы истории.
